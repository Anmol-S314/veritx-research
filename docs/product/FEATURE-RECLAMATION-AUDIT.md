### **The explicit answer §3 demands**

> What scientifically meaningful functionality would be lost if Phase-3
> Static Evaluate were implemented without reclaiming Wave E?

**Wave-E itself would not be lost — it already runs.** What would be lost is
its **product projection**. The product surfaces `completion_cycles`,
`completion_ns` and `completion_time`. Wave-E computes **seven** metrics. A
Static Evaluate built on the current metric registry alone would surface one
aggregate window number and silently drop:

- `makespan` and `critical_path` — the schedule-shape facts
- `resource_utilization` — where the fabric is idle versus saturated
- `request_latency` and its distribution — the per-request view
- `ttft` and `decode_step_latency` — the serving-relevant latencies
- `sensitivity` — the counterfactual "what would move this number" analysis

and it would lose the **honesty boundary** with them: `fidelity_warning`, the
`unsupported` list, and `predictive_validation: NOT_ESTABLISHED`. Those are
what stop an analytical estimate being read as a measured claim. Dropping
them is not a UI regression; it is a **scientific claim regression**.

**Classification:** Wave-E `CANONICAL_NOW` (P3). Wave-E **metric exposure**
`NEEDS_CANONICALIZATION` (**P0**).

partial, 0 unaudited.**

   Same label, opposite verdicts.

| **SERVING EXPERIMENT** | arrivals, traces, request ids, RR/LOAD policy, batching, batch size, prefill/decode progression, multi-instance, MoE dispatch/combine, PD (refused) |

| **BACKEND INTERNAL** | queueing, rank→endpoint, BookSim/analytical/ASTRA execution, profiling, liveness, subprocess protocol |
