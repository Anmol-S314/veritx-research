# FEATURE RECLAMATION AUDIT

> What scientifically meaningful capability existed anywhere in
> VERITX/SROTA history, and did our current canonical product architecture
> preserve it, intentionally reject it, or accidentally narrow it away?

Machine-readable companion: `docs/product/feature-reclamation-registry.yaml`
(generated by `scripts/gen_feature_reclamation.py`).

**This is not a product-design exercise.** Nothing was implemented. No
branch was deleted, archived or modified. No Phase 3 work was started.

---

## 0. Method, and the rule that governs every row

`capability-registry.yaml` states what the current canonical product can
truthfully do. This audit states what historically **existed** and what its
disposition should be. They answer different questions and neither replaces
the other.

**The critical rule:** a `NOT_AVAILABLE` row in the capability registry does
**not** prove a capability should be absent. Every current `NOT_AVAILABLE`,
`FUTURE_CONTRACT`, `ENGINE_ONLY` or omitted capability was searched in
history before being classified. Several rows did not survive that check.

**Capability was located in code and tests, never inferred from branch
names.** `third_party/` is kept separate from SROTA capability throughout:
a BookSim network backend existing is not canonical product exposure.

### Sources

The current integration branch and worktree; the **existing migration
ledger** `veritx_dse/application/inventory.py` (which already classifies
*paths* as `AUTHORITATIVE | MIGRATE | LEGACY_INTERNAL | TEST_ONLY |
DELETE`); the Gate 1–8 planning corpus; **84 branches** searched with
`git ls-tree` and `git grep`.

The audit **extends** the existing classification vocabulary rather than
inventing a parallel one: `inventory.py` classifies paths, this registry
classifies capabilities.

### Vocabularies

`historical_maturity` ∈ SEALED · TESTED · IMPLEMENTED · EXPERIMENTAL ·
CONCEPT_ONLY · ABSENT

`classification` ∈ CANONICAL_NOW · RECLAIMABLE · NEEDS_CANONICALIZATION ·
RESEARCH_ONLY · GENUINELY_NEW · REJECTED_UNSOUND

No generic `SUPPORTED` appears anywhere.

## 1. Topology audit (mandatory deep pass)

### 1.1 The current tree contradicts itself

```text
TopologyFamily      (compile_model.py:597)   MESH TORUS CONCENTRATED_MESH GEC FAT_TREE
MaterializedFamily  (topology_artifact.py:55) MESH TORUS RING CONCENTRATED_MESH
```

- `GEC` and `FAT_TREE` are **declarable but not materializable**.
- `RING` is **materializable but not declarable**.

That is an internal inconsistency independent of any historical question,
and it must be resolved before any family is added.

### 1.2 Historical breadth

BookSim carries `flatfly_onchip`, `dragonfly`, `qtree`, `tree4`, `fattree`,
`anynet`, `mesh`, `torus`, and more. The T3 track ships configs for eleven
topologies: `anynet16`, `cmesh16`, `dragonfly16`, `fattree16`, `flatfly16`,
`fly4`, `ftree`, `mesh4x4`, `qtree16`, `torus4x4`, `tree4`.

**BookSim breadth is not SROTA capability.** What matters is that the
canonical product narrowed to a five-value enum while the *routing and
projection* halves for arbitrary graphs remain canonical (`ROUTE-002`,
`ROUTE-003`, `CAP-ENV-BOOKSIM-ANYNET-V1`).

### 1.3 The custom-topology finding

`CAPABILITY-MATRIX.md` §18 records AnyNet as **exactly two capabilities** —
canonical route algorithm and backend projection — and states:

> **Neither is user intent.** There is **no AnyNet checkbox**.

So the machinery to *route* and *project* an arbitrary graph exists and is
canonical. What is absent is the **declaration** half (`FAB-007
custom / hierarchical topology`, `NO_CONTRACT`).

Planning did not reject arbitrary topology. It recorded that both halves
exist and that there is no user intent for it. **That is the shape of a
coherent-but-incomplete corpus.**

## 2. Topology synthesis audit (mandatory deep pass)

### 2.1 The synthesizers are in the current tree

```text
veritx_dse/synthesis/milp_topology_v2.py   traffic-weighted MILP (TMCF) + SA
veritx_dse/synthesis/bo_synthesizer.py     Bayesian optimization
veritx_dse/synthesis/iterative_synthesizer.py  RHO/GRPO iteration
veritx_dse/synthesis/event_objective.py    event-timeline objective
tracks/t3-topology/scripts/archive/milp_{topology,exactness,exactness_norm}.py
```

`milp_topology_v2.py` is not a toy. It reads a traffic matrix `T`, seeds
from the layout's base mesh for guaranteed connectivity, and solves a
Traffic-Min-Cost-Flow MILP deciding which extra candidate links to add —
minimising traffic-weighted hops under **radix**, **link-length** and
optional **diameter** budgets, with an explicit physical layout model
(`grid_xy`, `interposer_xy` with jitter) and wire/pipe cost pricing
(`set_costs`, `_edge_len`, `priced_geodesic`). It emits `<out>.anynet` for
BookSim and JSON for DSE.

### 2.2 It is classified, and the classification is honest

`inventory.py` already carries the row:

```text
path            veritx_dse/synthesis/
classification  LEGACY_INTERNAL
replacement     none in Wave C (synthesis science is Wave E)
```

Wave E became the **performance model**, not synthesis. The deferral landed
nowhere.

### 2.3 Planning did consider it — twice, and deferred it deliberately

- `INTENT-DESIGN-SPACE.md:512` — *"Refused with a stated return condition:
  `bayes`, `bo`, `milp`, `sa`, `rho`, `grpo` — 'Bayes/MILP only after
  deterministic correctness is established'."*
- `INTENT-REQUIREMENTS.md:384` — *"A future compiler that synthesises
  topology from requirements is a **new compiler-guidance contract** and is
  not assumed."*

**The decisive distinction:** planning's rejection targets MILP as a
**search method over a fixed design space**. `milp_topology_v2.py` is not
that — it **generates the topology graph itself**. Those are different
capabilities sharing a name.

So this is **classification B** — *still desired, awaiting
canonicalization* — with a planning-sanctioned return condition, **not**
classification C (accidental erasure). The corpus is coherent; it simply
never closed the loop it opened.

## 3. Routing audit (mandatory deep pass)

The three layers the brief asks to distinguish:

| Layer | Where | Status |
|---|---|---|
| backend routing function | `third_party/booksim2/src/networks/*.cpp` | many; **not** product exposure |
| canonical routing semantics | `model/routing.py`, `model/routing_materialize.py`, `model/routing_policy.py` | DOR-XY sealed; a full `RoutingPolicyDefinition` vocabulary exists |
| executed route evidence | `RunIntegrityView.route_realization` | `FIRST_HOP` scope only |

Findings:

- **DOR / DOR-XY** — `SEALED`, `CANONICAL_NOW` (`ROUTE-001`).
- **AnyNet Dijkstra** — `SEALED`; `core/route_artifact.py` replicates
  `AnyNet::route()` tie-break semantics exactly. `CANONICAL_NOW`.
- **Adaptive / MinAdapt / UGAL** — `model/routing_policy.py` is a full
  content-addressed `RoutingPolicyDefinition` with `PathMode`,
  `DecisionScope`, `CandidateMode`, `SelectionLocus`, `RandomnessMode`,
  `RoutingStateKind`, `RuntimeObservation`, `RoutingResourceRoleKind`
  (including `ADAPTIVE`) and `DeadlockProofObligation`. Meanwhile
  `model/router_behavior.py` states: *"Explicitly absent: escape/adaptive
  priority, routing-action priority, congestion thresholds, MinAdapt/UGAL
  arbitration, hidden QoS priority."*

  **A canonical adaptive-policy vocabulary exists while the behaviour
  artifact declares adaptive arbitration absent.** `ROUTE-009` says
  `FUTURE_CONTRACT`. One of those is wrong; the audit does not presume
  which. `NEEDS_CANONICALIZATION`, P1.

- **MCLB / ILP min-max-load** — appears in `cli.py` and
  `tools/deadlock_routing.py` only. `EXPERIMENTAL`, `RESEARCH_ONLY`.
- **Valiant** — a **single mention** in `model/packet_format.py`. That is
  not an implementation. `CONCEPT_ONLY`, `RESEARCH_ONLY`. Recorded
  explicitly so a future reader cannot mistake a keyword hit for a feature.
- **Escape VC designation** — `SEALED` and canonical
  (`VCAssignmentArtifact.escape_vcs`, tested by `test_adaptive_escape.py`,
  `test_channel_vc_cdg.py`), yet `ROUTE-008` says `IMPLEMENTATION_GAP`.
  Same class of contradiction as adaptive routing.
- **RCU / in-network reduction** — **zero matches** for `rcu`/`RCU` in any
  SROTA source file on any branch. `ABSENT` historically →
  `REJECTED_UNSOUND`. The Gate-5 removal was correct: there was never an
  implementation, only an intent field. This is the audit's cleanest
  rejection.

## 4. Workload-parity audit

Two layers, and the brief's list spans both:

```text
evaluation side   veritx_dse/workload/graph.py
                  KIND_COMPUTE KIND_COLLECTIVE KIND_P2P KIND_MULTICAST
                  KIND_EXPERT_BEGIN KIND_EXPERT_END
                  KIND_PIM_CHANNEL KIND_PIM_END                    (8 kinds)

design intent     model/compile_model.py::WorkloadV3
                  collectives: allreduce allgather reducescatter
                               broadcast alltoall                    (5 kinds)
                  + DependencyGraph
```

So **P2P, MULTICAST, EXPERT_DISPATCH/COMBINE and PIM are expressible
downstream but not declarable as canonical Design intent.**

`INTENT-WORKLOAD.md:122–129` already reconciled the **Phase-9 grammar**
against Wave-D:

| historical | disposition | canonical |
|---|---|---|
| `P2P` | RENAMED_EQUIVALENT | P2P (roles TRANSFER/SEND/RECV) |
| `MULTICAST` | EXACT_EQUIVALENT | MULTICAST |
| `EXPERT_BEGIN` | RENAMED_EQUIVALENT | EXPERT_DISPATCH |
| `PIM_CHANNEL` / `PIM_END` | PARTIAL_EQUIVALENT | MEMORY |

That reconciliation is about the **old** grammar. It does **not** cover the
`WorkloadV3 → Wave-D` gap, which is a new finding: the current intent
vocabulary is narrower than the canonical graph it must lower to.

**PIM specifically.** Planning records it `PARTIAL_EQUIVALENT → MEMORY`,
and the registry says `MEM-007 PIM NOT_AVAILABLE / LEGACY_ONLY`. But
`KIND_PIM_CHANNEL` is live in the Wave-D graph **and** the ASTRA backend.
`LEGACY_ONLY` understates it. This is the critical rule firing directly: a
`NOT_AVAILABLE` row whose historical evidence is stronger than the row
implies.

## 5. Current-planning contradiction pass

For every historical `SEALED` / `TESTED` / `IMPLEMENTED` capability the
corpus classifies as absent, future or not-modelled:

| Capability | Planning says | Audit finds | Case |
|---|---|---|---|
| topology synthesis (MILP/SA/BO/iterative) | deferred as a *search method*; "new compiler-guidance contract … not assumed" | real generator, present in-tree, `LEGACY_INTERNAL`, deferral landed nowhere | **B — awaiting canonicalization** |
| custom / arbitrary topology | `FAB-007 NO_CONTRACT`; "no AnyNet checkbox" | route + projection halves canonical; only declaration absent | **B** |
| adaptive / MinAdapt / UGAL | `ROUTE-009 FUTURE_CONTRACT` | canonical adaptive-policy vocabulary exists; behaviour artifact excludes it | **B** (or a row is wrong) |
| escape VC designation | `ROUTE-008 IMPLEMENTATION_GAP` | sealed, canonical, tested | **B** (or a row is wrong) |
| PIM | `MEM-007 LEGACY_ONLY` | live in Wave-D graph and ASTRA backend | **B** |
| multiplane | `FAB-005 FUTURE_CONTRACT` | five BookSim configs; **zero** source mentions | **A/C-lite** — correctly `RESEARCH_ONLY` |
| RCU | `ROUTE-011 FUTURE_CONTRACT` (removed v4) | **zero** historical implementation | **A — correctly rejected** |
| Valiant | `ROUTE-010 FUTURE_CONTRACT` | one keyword mention | **A** — correctly `RESEARCH_ONLY` |

**No case of outright accidental erasure was found.** Every `B` case is a
documented deferral whose return condition was never met, or an internal
contradiction between two rows of the current tree. That is a materially
different finding from "capability was lost", and it is the more useful one:
the corpus does not need repairing, it needs *completing*.

## 9. What this audit already changes

Three things are actionable today without any new capability work:

1. **`MaterializedFamily` / `TopologyFamily` disagree** inside the current
   tree. Fix that before adding families.
2. **`ROUTE-008` and `ROUTE-009`** contradict sealed canonical code. One of
   the two is wrong in each case; determine which.
3. **`MEM-007 PIM`** is `LEGACY_ONLY` while `KIND_PIM_CHANNEL` is live in
   the Wave-D graph and the ASTRA backend. Reclassify or justify.

None of these is a new feature. They are the corpus disagreeing with itself,
which is exactly the class of defect a reclamation audit exists to surface.

## Verdict

Every capability discovered in this pass has historical evidence, a current
disposition, a classification and a required action. But **39 of the
required domains were not reached**, and a reclamation audit cannot close
while domains remain unsearched — an un-audited domain is
indistinguishable from an absent one to anyone reading the registry.
