# Reusing inference-time communication traces

## Summary
No public artifact located is a faithful measured multi-GPU VLA-inference packet/link trace that can be dropped into BookSim. The strongest fast path is to reuse public PyTorch/Kineto/Chakra collection code and generate a real distributed inference trace on suitable multi-GPU hardware; given this host's CPU-only PyTorch and one 4GB GPU, that is not possible locally. For an immediate proxy, PACC's public traces/code and existing Chakra sample traces are accessible, but must be labeled as training/synthetic or single-GPU evidence rather than VLA collective traffic.

## Findings

1. **PyTorch profiler / Flight Recorder — best collection method, not pre-captured VLA evidence.** PyTorch distributed docs expose Flight Recorder configuration/API for recording collective operations and rank/process-group metadata; ordinary profiler/Kineto gives measured operator/kernel timing and framework-visible collective events, not physical wire packets. [Distributed communication](https://docs.pytorch.org/docs/stable/distributed.html), [Flight Recorder tutorial](https://docs.pytorch.org/tutorials/intermediate/debug_hangs_with_flight_recorder.html), [Profiler](https://docs.pytorch.org/docs/stable/profiler.html). **Support:** direct evidence. **Confidence:** high. Requires an instrumented application, CUDA-enabled runtime for GPU activities, and an actual distributed process group for real multi-rank events. Profiler output requires conversion: each collective's participants and byte count do not directly specify per-hop packets, routes, flits, or cycle injection times.

2. **Nsight Systems — complementary observed runtime evidence.** NVIDIA documents tracing/export of CUDA/NCCL activities and export to SQLite/JSON; the timeline measures API/GPU activity and can expose NCCL collective execution metadata, not packet-level link transfers. [Nsight Systems User Guide](https://docs.nvidia.com/nsight-systems/UserGuide/index.html), [Analysis Guide](https://docs.nvidia.com/nsight-systems/AnalysisGuide/). **Support:** direct evidence. **Confidence:** high. Requires compatible NVIDIA GPU/driver/runtime and profiling permissions; installed local Nsight version alone cannot create multi-GPU evidence. The user's Nsight 2025.5.2 predates documented advanced NCCL tracing introduced in 2025.6.1; basic tracing may still be available. Not BookSim-ready without assumptions for collective expansion, endpoint mapping, timing, packetization and routing.

3. **PACC — actual two-rank NCCL events, but ambiguous workload provenance.** [Pinned revision](https://github.com/lynxarv/PACC/tree/f2eed8c27fa0a28d027d8faf153e59e92fd80e45) has DeepSeek-R1-Distill-Qwen-7B FSDP traces with 29 AllGather CPU calls and 29 `AllGather_RING_LL` GPU kernels per rank, world size 2, V100S-PCIE, NCCL 2.27.5, FP16 input tensors and measured GPU kernel durations. The files contain no detected backward events, but PACC documents multi-GPU FSDP captures as training and does not tie the selected forward-only collector to these exact files. Treat as real NCCL-event evidence with unresolved workload phase—not an accepted inference or serving trace. No physical packet/link trace; no root license found. Details/hashes: `docs/research/inference-capture-audit.md`.

4. **A particularly relevant measured vLLM inference paper.** Xu et al., [“Characterizing Communication Patterns in Distributed Large Language Model Inference”](https://arxiv.org/abs/2507.14392), profiles Llama models in vLLM on **4×H100 with NVLink**. The paper reports profiled all-reduce/gather and pipeline point-to-point counts, sizes and volumes for TP/PP/hybrid layouts, and compares them against analytical predictions. This is measured inference communication-operation evidence, not a raw per-packet trace; no public code or raw trace repository was found. Its tables can directly check our collective counts/byte accounting, but cannot identify BookSim injection cycles, routes, or flits without an explicit projection.

5. **An open measured vLLM/H200 inference dataset.** The [CAL26-NCCL-GEMM repository](https://github.com/yechen3/CAL26-NCCL-GEMM-data) and its [CC-BY-4.0 Zenodo release](https://zenodo.org/records/21925183) provide public, plot-ready inference data; the Zenodo record documents **4×H200 vLLM inference** and links 13 raw Nsight Systems captures (1.7 GB) on [Hugging Face](https://huggingface.co/datasets/liu2550/CAL26-NCCL-GEMM-data). I downloaded and inspected the 1 MB Zenodo archive: inference CSVs include CUPTI-sampled `nvlink_GBps` vs. time for a vLLM Qwen3-30B DeepEP run, plus compute-kernel slowdown data. The series is published as NVLink bandwidth, but the DeepEP-panel values are only about `1e-7` to `5e-7` GB/s while the figure-data README names a 900 GB/s peak; the exporter divides its `nvl` source column by `1e9`, and the raw counter unit/scale has not been independently established. Treat this as a lead to measured profiler data, **not as a validated bandwidth target** until the scale is reconciled. It is not per-collective or per-packet source/destination traffic. The separately hosted raw captures were not retrieved in this pass; the published plot-data is available.

6. **Chakra + ASTRA-Sim — useful trace standard/converter, not proof that bundled examples are captured runtime traffic.** [MLCommons Chakra repository](https://github.com/mlcommons/chakra) (MIT) supplies schema, PyTorch/Kineto conversion/linking tools; [ASTRA-Sim workload docs](https://astra-sim.github.io/astra-sim-docs/getting-started/argument-workload-config.html) say it accepts per-NPU Chakra ET files `{prefix}.{npu_id}.et`, with bundled example workloads. Chakra ET represents graph operations, communication, timing and dependencies. Public traces may encode measured or generated workloads depending on provenance; the format itself does not certify measurement. **Support:** direct evidence. **Confidence:** high. Use a measured ET if provenance and target workload match; otherwise classify as projected/synthetic. Chakra ET is not the local BookSim packet record; conversion needs rank-to-node mapping, communication algorithm expansion, flit sizing and cycle conversion.

7. **Evidence categories and BookSim fit.** (a) Model compute timings: profiler/Kineto device events directly measure kernels under observed setup, not network traffic. (b) Framework collective calls/tensor metadata: PyTorch Flight Recorder/Nsight can observe runtime calls, ranks, sizes/shapes; these prove calls, not wire transfer pattern. (c) Physical link/NVLink/NIC counters: CAL26 publishes an inference counter series, but its NVLink scale is suspicious and unverified. No reviewed public artifact establishes per-packet source/destination/time/flits for the target model. Counters are aggregate telemetry, not packet records. (d) Synthetic/projected NoC traffic: ASTRA-Sim examples, FX-derived traces, or expanded collectives are model-generated inputs, not observed physical traffic. BookSim input `cyc src class dst flits` requires packetized events and topology-node mapping; a collective event cannot uniquely determine these without explicit algorithm/routing/packetization assumptions. **Support:** direct distinctions plus researcher inference for conversion implications. **Confidence:** high.

## Contradictions and quality checks
The CAL26 release labels its series `nvlink_GBps` and describes a 900 GB/s peak, but every inspected inference and training NVLink panel remains below `1e-6` GB/s (e.g. DeepEP inference peaks at `6.1897e-7`; training Ring ReduceScatter and A2A also peak below `8.6e-7`). Its exporter divides `nvl` by `1e9`, but the raw counter unit was not established in the release. Do not calibrate on these values until that scale is resolved. The Llama paper's operation counts/sizes are internally consistent with its reported tensor shapes and byte sizes.

## Missing evidence
No qualifying public VLA/transformer multi-GPU inference raw collective trace with verified provenance, or public per-link packet trace, was identified. CAL26 counter data is published but its NVLink magnitude is unverified. Exact trace artifact license terms and per-file provenance in PACC should be checked before reuse. BookSim parser's exact local class-field convention was not independently inspected here; avoid claiming an off-the-shelf converter.
