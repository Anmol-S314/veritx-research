## SROTA playback follow-up

Reproduced with chrome-devtools-axi: the original projected player treated a shared-wire topology with zero point-to-point channels as if it were an ordinary link graph. Measured activity mixed subnet labels, and 995 windows produced an excessively wide matrix.

Changes: bounded observed native receipt/send capture and replay; separate native subnet selection; SROTA local-first port labels; shared-wire driver/tap table; window counts summed into at most 80 display buckets, peak lanes preserve maxima; historical topology fetch never falls back to a different active revision.

### Shared-wire projection (replaces the refusal)

The earlier amber notices were a stand-in, not a fix. Shared-wire playback and attribution now run on the fabric's own resources:

- **Inspector gap closed.** `compile_result_view._routing` silently dropped the certified v3 route: a `ShapePolicyRoute` exposes `choices`/`partition_to_vcs`/`shape_of_partition`, not `routing_classes`/`entries`, so the inspector reported `routing_classes: []` and no route at all. It now emits `shared_route` (canonical v3 payload plus `route_artifact_id`). `compile_result_is_current` refuses a frozen payload whose fabric has shared wires but no `shared_route`, so a stale projection cannot be served. `product._stored_compile_result` also pins the recorded `router_route_hash` when re-deriving.
- **Correct binding.** v3 resource ids are route-level port identities, not topology array indexes. The client binds a decision by (driver, tap → landing router) and fails closed unless exactly one topology wire matches. Unit test covers the wrong-resource case, plus missing choices, unknown endpoints, invalid classes and loops.
- **Plane semantics from the executed config.** Class→plane comes from the sealed `class_subnet`, the grid from `k`/`c`, and Plane C availability from `srota_planes`. Plane C is projected as the native private XY channel (one cycle per cell), never as an express-wire alias. Plane D walks certified v3 decisions, holding one adaptive shape for the whole route; both shapes remain selectable because the runtime choice is telemetry-driven and is not claimed.
- **Contention kept honest.** Distinct taps on one wire aggregate onto the single shared resource (tap breakdown retained), because taps contend for one slot. Attributed flits are requested flits summed over projected hops, labelled as attribution, not measured utilization.
- **Rendering.** Solid teal = driver-to-farthest-tap bus with square drop taps; dashed amber = private Plane C channels. Playback, next-transfer, plane filter and the attributed-resource table are all driven by the same projection.

Verified on Flow test 05 (`p-a34dda8428eb`, run `01a17892-…`): 8,928 sealed trace rows, 0 rejected, 50 resources touched, Plane C 39,060 and Plane D 13,020 attributed flit-hops. An independent Python walk of the same trace, config and certified decisions reproduces those totals exactly for both shapes. Latest matrix run: **5 passed, 1 skipped, 53.7s**; `test_shared_route_inspector.py` and `test_compile_result_view.py` pass (67 checks with the gateway/serve-product suites).

### Measured counters joined to wires (executed dump, not an assumed port order)

The native SROTA port index is not a compass direction and not the topology `src_port`; one port carries every tap of exactly one shared wire. Rather than hardcode that order, the join is read from the run's sealed `routing.dump` (512 rows of `src_router dst_node next_router port drop vc_start vc_end`):

- `parseRoutingDump` accepts only the exact native shape and treats `drop = -1` as the local-eject marker.
- `buildPortWireMap` binds `(driver, port)` to a wire only when every dumped landing on that port is a tap of exactly one declared wire, each wire is driven by exactly one port, and the remaining ports match the declared seat capacity. Anything else is a refusal with a reason, never a partial map.
- On Flow test 05 this yields **48 of 48 wires, 32 local ports, 0 problems**, and `drop` proves to be the native tap index.
- The map is gated to subnet 0 for the same reason: the dump is written by the subnet-0 routing function, so Plane C ports must not borrow it.

Cross-check, which is the real prize: measured counters now reconcile with the projection exactly. Measured fabric totals are 13,020 flits on joined Plane D ports, 39,060 on unjoined control-plane ports, and 62,496 on local eject; injected (62,496) + projected hop flits (52,080 = 13,020 D + 39,060 C) equals the measured 114,576. The E2E test asserts this equality by summing the sweep per plane and comparing it with the measured attribution panel, so a projection that drifts from the simulator now fails a test.

Still missing: contention, arbitration and queueing are not modelled, so projected timing is not an expected completion time; the declared route remains DERIVED, not observed; Plane C port order is not certified by any bundle here, so those counters stay unjoined with a stated reason rather than a guessed neighbour; wire counters record driver transmissions, so the tap a flit exited by is still not measurable.
### Observed hops: a stride sample, and a verdict per flit

The first watch capture selected a prefix of native packet ids (`{0..7}`), which is a
cold-start sample of a run, not a sample of the run. Two changes replace it.

**The sample.** `observed_watch_plan` counts the declared packets in the run's own
trace and watches `every Nth` id, capped by `OBSERVED_WATCH_BUDGET`; the rule, the
declared count, the stride and the sampled ids are recorded in
`stats.observed_hop_capture.sample` beside the capture's sha256, size and scope.
Flow test 05 (8,928 declared packets) samples every 93rd id: 96 packets, 579 watched
flits, 2.1 MB of sealed log instead of a cold-start prefix. An unsampled call emits
no `watch_out`/`watch_packets` keys at all, so no empty watch file is left behind as
a misleading artifact.

**What the ids are.** `Received flit N` prints `f->id`, which in this fork is the
global *flit* id, not the packet id — `Retiring flit 61870 (packet 8835)` is the
proof. `watch_packets` selects packets, every flit of a selected packet is logged,
and each watched flit carries its packet's path. The frontend join key is therefore
the flit id, and the UI says "watched flits" rather than "sampled packets".

**The verdict.** Each watched flit is checked twice, and the two claims are counted
separately because they rest on different evidence:

| Claim | Evidence | Applies to |
|---|---|---|
| route | certified v3 decisions, the recorded router sequence and the native hop counter | both planes |
| wire | the executed `routing.dump` port-to-wire map | subnet 0 only (the dump is written by the subnet-0 routing function) |

Subnet 1 therefore reports *route only*: verified as a route, unverified as wires,
with that reason stated. Reporting it as a wire mismatch would be a fabricated
failure, and the first version of this check did exactly that — 178 false
"mismatches" that were really a `C:a:b` hop token compared against a wire number.
Local deliveries are separated from ambiguity: a single router receipt is ambiguous
on its own, and `Retiring flit N (packet P, src, dest, hops)` from the same sealed
capture resolves it. A flit whose recorded hop counter contradicts the length of the
route that matched is reported as a mismatch, not a pass.

Flow test 05 over all 579 watched flits: **277 route-verified (99 also wire-verified),
302 verified local deliveries, 0 mismatched, 0 unverifiable** — every watched flit is
accounted for, which the E2E asserts as `route verified + local verified == watched`
with no `Unaccounted` cell.

Still missing: this is a sample, not a full hop trace, and it is per flit, so it does
not measure queue occupancy, arbitration or contention; timing remains a projection.
Subnet 1 wire identity needs a subnet-1 routing dump that the fork does not write.

### Persisted qualification refusals used to outlive the capability state

The CMesh requirement was closed by a concurrent change
(`docs/product/CMESH-REQUALIFICATION-2026-10.md`; registry record now `QUALIFIED`;
producer bytes reproduced from a clean build; 30 projection tests pass). The Flow
test 04 revision kept the refusal it recorded when it was compiled —
`CERTIFIED_BOOKSIM_CMESH_DOR_XY_V1 is a WITHDRAWN capability` — and
`submit_evaluation` replayed it, while the evaluation *plan* for the same revision
reported `READY`. That is a real product inconsistency: a revision pins the
qualification verdict of its compile, so a requalification leaves stale refusals
behind with no signal that they are superseded.

Fixed by re-deriving a *stored refusal* instead of replaying it. A revision keeps
the assessment its compile produced, and that snapshot stays on disk untouched, but
`_assessment_for_revision` now recomputes when the stored verdict is `UNSUPPORTED`
and reports the fresh verdict with a `superseded_refusal` record beside it (recorded
support, recorded reason, re-derivation time, and what supersession means here). A
refusal the live state still reproduces is returned unchanged, so this can never
turn a real refusal into a pass.

Verified end to end: `POST /revisions/p-d5d732f4f8de-r02/evaluate` — the revision
whose stored record says `CERTIFIED_BOOKSIM_CMESH_DOR_XY_V1 is a WITHDRAWN
capability` — is now accepted and its job completes with `run_status: EVALUATED`.
`test_superseded_refusal.py` pins both directions (a superseded refusal, and a
refusal that still applies), and the launch panel renders the recorded refusal
beside the live verdict when the store carries one. The E2E no longer recompiles to
work around it, and it now asserts that the plan and the submit gate agree: the
blocked fixture's plan says `BLOCKED` *and* its `evaluate` call is refused with the
same reason.

Refusal coverage was not dropped when that obligation closed: Flow test 08 is a
concentration-3 variant whose `seat_capacity` falls outside the certified envelope,
and the plan refuses it by name
(`UNSUPPORTED: certified mesh-DOR covers seat_capacity 1 only (router 0 has 3)`)
with `backend: null`, no run and a disabled launch row.

### Analysis sections stay visible, and say what they need

The section list used to disappear when no run was loaded, leaving a page that
looked broken. It now renders in every state, and each section states its own
requirement in three rows — what it reads, what this project has, and why it is
empty — with the same line every other unavailable value carries: *nothing is

### A written run is not "nothing written"

Two defects made a failed evaluation unreadable:

- `_run_federated_evaluation` collapsed every non-`EVALUATED` outcome into
  `REFUSED`, so a backend that crashed was reported as a refusal.
- the in-process job runner stored `error_message: None` for that state, and the
  panel then printed "REFUSED: No message supplied. Nothing written." — while a
  run record *had* been written, carrying the precise reason (in the case that
  exposed it: `could not spawn the BookSim process: [Errno 2] No such file or
  directory: 'third_party/booksim2/src/booksim'`).

Now the run's own status decides the job state (`FAILED` vs `REFUSED`), the run's
reason travels in the job result and becomes the job's error message, and the panel
names the run when one exists instead of claiming nothing was written. Two unit
tests pin the mapping (failed-with-run, refused-with-run, completed-without-error).

### A stale job could stand in for the launch

Observed once: after Launch the panel showed a *previous* job as
`FAILED · interrupted by gateway restart` and never reached "Run published", while
the store recorded the newly submitted job as COMPLETED with a run. The run was
always written, so this was a UI defect rather than a measurement fault.

The cause was in loading a project: after the project record arrives, the workspace
asks for that project's jobs and resumes any non-terminal one by calling
`trackEvaluation`. That call arrives *after* the user's own launch, so it replaced
the panel's job with an older record and left the new one unwatched — a job that is
already finished then presents as a failure of the click. It also picked the first
matching job rather than the newest.

Adoption is now a pure, tested decision (`src/jobAdoption.ts`): it is skipped while
an explicit track is in this session's project load, only non-terminal jobs are
eligible, and the newest eligible job wins. `trackEvaluation` counts a user action;
the adoption path calls the internal runner so it does not look like one.

Coverage note: the decision is unit-tested, but the *happy path* — opening a project
while a job runs and seeing it resumed — cannot be asserted live here. A network
evaluation finishes in about three seconds, faster than a cold page load, so every
attempt observed the job already terminal and the app correctly resumed nothing.


## Findings / remaining work

1. Analysis sections now stay visible without a selected run and name what each section needs; the draft-mode test asserts the strip, the per-section requirement and the unavailable-value line.
2. The CMesh catalog preset uses frozen v2 semantics and is unsuitable as an evaluation-ready starter. The explicit v3 fixture now compiles and evaluates under the requalified profile, and the out-of-envelope variant (Flow test 08) carries the refusal coverage. Qualification was not bypassed.
3. The original MoE catalog entry declares bare `LOCAL` operands, which lowering refuses by name once more than one HBM pool is declared (`bare LOCAL is ambiguous with multiple HBM controllers; use LOCAL:<declared-device-id>`, pinned by `test_memory_lowering.py::test_multi_hbm_needs_an_explicit_device`). So the preset is *not evaluable out of the box* rather than unguarded: nothing guesses a pool. The Flow test 02 fixture now explicitly assigns nonzero operands to `LOCAL:{owner % 4}` as a synthetic test placement policy, compiled as r02. Network + system + DRAM execution and sampled panels pass in the strengthened live browser test (21.5s). Fixed missing DISPATCH_EVENT_LIMIT import in ramulator_dispatch and empty controller-cycle handling; two live multi-pool archive/replay tests also pass. This does not change the original catalog entry or imply model-authentic placement.
4. Adopting the same link width may be a no-op and leaves the draft clean. Test selects a genuinely different patch instead of assuming every adoption dirties the draft.
5. Backend tab availability varies by captured evidence. Successful rendering is not proof that every tab contains measured data.
6. No claims yet for topology-family study, multiobjective recommendation, cancellation, responsive visual quality, or every recovery path.
